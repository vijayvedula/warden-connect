warden-connect · adoption

A control plane nobody
asked for, adopted one rung at a time

Every security control competes with the option of ignoring it. So the interesting question about warden-connect is not what it enforces — it is what the smallest useful piece looks like, and whether a single developer can reach it alone, in an afternoon, without asking permission from anyone.

Five rungs · six readings · seven topologies Grounded in the shipped binaries

01

The paradox that shapes the whole design

Start with the failure mode, because it decides everything downstream.

A team wants an agent to read balances from a payments service. Today that means a ticket, an unclear approver, a two-to-three week wait, and eventually a shared credential copied from a wiki page. The security value of that process is close to zero — nothing is enforced at the end of it — but the cost is real, so engineers route around it. They deploy the agent and skip the ticket.

Which produces the actual state of most estates: no register, no expiry, no scoping, and a security process everyone agrees exists.

So a control plane for agent connections has an unusual constraint. It cannot be introduced as a gate, because gates get bypassed. It has to be introduced as something that is useful before it is mandatory — and each step toward enforcement has to pay for itself, on its own, to the person taking the step.

the design rule The developer journey must get faster, or the security journey never happens. Every rung must either shrink a surface or shorten a wait. A rung that does neither will be removed by the organisation, whether or not you agree with them.

What follows is that constraint taken seriously: a ladder where the first rung is a pure function you run on your laptop, the last rung is estate-wide containment in under a minute, and you can stop on any rung indefinitely.

02

The developer's ladder

Five rungs. Each is a superset of the last. Each is independently valuable, individually reversible, and none requires the next one to exist.

Read the third tag on each rung carefully — it is the one that makes this a gradient rather than a rollout.

1
minute one · no state, no server, no registration

Give a tool surface a name

The first thing warden-connect does is turn a tool manifest into a pin: a canonical serialisation, then a hash. Feed it an MCP tools/list response, get back a digest over the exact fields that were contracted — nothing else.

# a pure function. no config, no daemon, no permission. connect canon tools.json --kind mcp surface_digest sha256:230c1f4acb7bf… get_balance sha256:8a1e… list_transactions sha256:c40b…

Run it twice against the same server on different days and the digests differ if anything in the contracted subset changed — including a tool description, which is where prompt-injection payloads live. That is a rug-pull detector built from one command and a file you keep.

2
hour one · a directory on disk

Know what you actually have

Register the agents and servers you already run. State is an append-only log under --root plus an in-memory projection — a directory, not a database, so there is nothing to provision and nothing to ask for.

connect register server --endpoint https://payments.internal/mcp \ --owner human:priya --zone internal.payments --surface tools.json connect register agent --card recon-agent.json --owner human:priya \ --zone internal.apac-ops connect entities connect posture --unattested # who cannot prove what they claim

Nothing is enforced yet. What you gain is the thing no estate has: a list, with owners. Every lifecycle transition lands in a tamper-evident hash chain, so connect audit verify can prove the list was not edited after the fact.

get: the register + evidence cost: a CI step ↓ stop here: this is a real deployment
3
day one · still entirely local, still just files

Turn an approval into an artifact

Now the core loop. A request names both parties, the exact tools wanted, and why. Policy answers instantly whether it auto-approves. An approval is a detached signature from a named human's key — not a row in a table an operator with database access could write.

connect request --from agent:recon --to server:payments \ --tools get_balance,list_transactions --justify "nightly reconciliation" \ --ttl 30d --issuer-key issuer.pem --kid k1 req_7f3c → require_approval (write surface: none · callee tier 3) connect approve req_7f3c --by human:cecil --approver-key cecil.pem minted conn_1a9b → contract.jws exp +30d connect verify contract.jws --issuer-pub issuer.pub --kid k1 \ --mediator-id warden:mediator:apac-ops --issuer-id https://connect.internal

The payoff is the exit code. 4 means the artifact is not trustworthy; 3 means you asked for too much; 5 means the surface looks poisoned. CI can now fail on the difference without scraping stderr — and a contract that expires is a review that actually happens.

get: signed, expiring permission cost: an issuer key ↓ stop here: enforcement still optional
4
week one · the first rung that changes behaviour

Put the contract on the path

connect-mediate is one process that composes unmodified Warden core with a connect decorator. Your MCP client points where it already pointed. No manifest edit, no second network hop.

connect-mediate --upstream "python payments_server.py" \ --mediator-id warden:mediator:apac-ops --issuer-id https://connect.internal \ --caller agent:recon --callee server:payments \ --contract contract.jws --issuer-pub issuer.pub --kid k1 \ --observe # record findings; deny nothing. start here.

Two things change. tools/list returns only the contracted tools — the server offers three, the agent sees two, so the wrong tool cannot be called by accident. And an uncontracted tools/call is refused with WC-4002 before the upstream is ever spoken to.

Verified end to end: with Warden core's own policy set to permit everything, warden-connect alone blocks the uncontracted tool and the upstream logs zero executions of it. The two layers are genuinely independent — which is the whole point of the split.
get: deny-by-default cost: a sidecar ↓ stop here: no control plane needed
5
month one · the estate, not the repo

Make it estate-wide, and make containment one verb

Run the control plane. Mediators pull their contract sets and acknowledge exactly what they applied — pull, not push, because a lost push is silent whereas a missed pull shows up as ACK lag you can alert on.

connect serve --listen 0.0.0.0:8443 --issuer-key issuer.pem --kid k1 connect-mediate … --contracts https://connect.internal --token $T --refresh 5 1 contract(s) installed, set sha256:230c1f4acb7bf seq 8, acked connect quarantine agent:recon --reason "SIEM: anomalous egress" \ --approver human:sam --approver human:dev # dual control

One verb, whole estate. Every contract the party holds — inbound and outbound — revoked across every mediator, with per-mediator confirmation. Mediators that do not confirm are reported as unconfirmed and fail closed themselves, because a containment tool that assumes success manufactures false confidence.

get: sub-minute containment cost: a service to operate — top rung

Notice what is not on this ladder: a big-bang migration, a mandate, or a step where the developer's total time goes up. Rung 2 costs a CI step they do not perform by hand, traded against weeks of waiting they no longer do. The friction budget is net negative — and it has to be, or rung 4 never gets permission to change behaviour.

03

What a contract is, precisely

Before the enterprise view makes sense, one idea has to be exact, because every team gets it wrong in the same direction on first contact.

A contract is a ceiling, never a grant. Holding one does not authorise a call. It bounds what a call could possibly be.

callee declares
get_balance · list_transactions · wire_funds · …
contract surface
get_balance · list_transactions
token scope
read-only, this tenant
policy decision
permitted now, this caller
effective

Each layer can only narrow. warden-connect owns the relationship boundary — may these two parties be introduced at all, and on what surface. Warden core owns the action boundary — may this specific call proceed right now. Neither can widen the other, and removing either one does not silently widen the remaining one.

This is why the two systems couple through two signed artifacts and one identifier — a session token, a connection contract, and a cid — rather than a shared library. A team can adopt warden-connect with no Warden core deployed at all, and a team can adopt Warden core and substitute something else for the relationship layer entirely. That independence is not politeness; it is what lets adoption start anywhere.

04

Six teams, one artifact, six different readings

Here is the property that makes this a control plane rather than a tool. Enterprise teams do not agree on process, tooling, or vocabulary — and they do not have to. They agree on one object, and each reads it for what they need.

agent developers

A smaller surface to reason about

They read the contract as fewer tools in the list. Not a restriction — a narrower API, with the footguns removed. Fewer accidental calls to the wrong tool, and a request that auto-approves in seconds when it is internal and read-only.

connect request --tools … --justify …

platform / infrastructure

A config distribution problem

They read it as a sidecar in a base image and a pull loop with an ACK. Their concern is that a mediator with a broken config refuses to start rather than passing traffic — and it does, with WC-8004.

connect-mediate --contracts … --refresh 5

security architecture

An approval that is its own enforcement

They read the signature. Approving the relationship rather than every call is what makes reviewing 40–60 requests a month survivable — and the approval is the mechanism, so it cannot decay into a filed ticket nobody implements.

connect approve req_… --approver-key …

secops / incident response

A blast radius and a kill switch

At 03:00 they read it as the reachable set. Scoping goes from "ask three teams and grep deployment repos" to one query, and containment from hours to one verb with per-mediator proof it landed.

connect quarantine agent:x --reason …

risk & compliance

A register that signs itself

They read the evidence chain. Every lifecycle event hash-chained, checkpoints signed, and an as_of query — so "what was permitted on the 14th" is answerable to the minute rather than reconstructed from tickets.

connect audit verify · connect export

the provider team

A customer list, and a change budget

Often forgotten. The team that owns the MCP server reads contracts as who depends on which of their tools — so they learn the cost of a breaking change before shipping it, and pinning turns silent drift into a conversation.

connect posture --drift
Why this matters for adoption: no team has to adopt another team's workflow. The artifact is the integration point, so the platform team's rollout and the compliance team's export do not need to be sequenced with each other, and neither blocks the developer on rung 3.
05

Where you put the enforcement

Seven shapes. The one to look at first is the top row, because it is the one people assume must be a mistake.

TopologyShapeWhen it is rightWhat you give up
Control plane only No data plane at all. Register, admission, pins, drift, posture, exports, quarantine orders. The wedge. Estates that want the register and the evidence before they want behaviour change. Nothing is enforced. Contracts are issued but unverified, tools/list unfiltered, quarantine notifies rather than cuts. Honest visibility, zero behaviour change.
Sidecar preferred One connect-mediate process per agent runtime. Default. Surgical containment — killing one process cuts one agent. More instances to operate.
Shared gateway One mediator fronting many agents. Brownfield, simpler ops, an existing chokepoint. Concentrated trust boundary; containment relies on per-cid revocation rather than process isolation.
Third-party enforcement Someone else's Envoy filter, API gateway plugin or agent framework runs the eleven checks. An egress proxy already exists and should not be duplicated. Conformance is on them — connect verify plus the 19 published vectors are the suite they must pass.
Egress mediator Dedicated mediator on the org boundary. Partner and public zone crossings. Must not be the only mediator — internal relationships still need governing.
Federated A control plane per organisation, federated trust anchors. Cross-org agent-to-agent. Trust-anchor lifecycle becomes a first-class operational concern.
Air-gapped Contracts pre-issued as signed bundles; no control-plane call. Regulated or offline estates. Expiry is hard; revocation depends on bundle refresh.

That first row is a deliberate product decision and it is worth defending. An estate that deploys the register and nothing else gets a truthful inventory, owners, pins, drift detection and an evidence chain — and enforces nothing. It says so, loudly, in connect posture.

the principle underneath Honest visibility beats fake enforcement. A control that reports success while doing nothing is worse than no control, because nobody investigates something that looks fine.

And the fourth row matters for a different reason: you do not have to run our data plane at all. The artifact format, the canonicalisation and the eleven verification checks are specified, and the conformance vectors are published. An organisation with an existing egress proxy can implement the checks there and still interoperate with everyone else's control plane.

06

Rollout patterns by the shape of the organisation

The ladder is one developer's path. An estate has several of them running at once, and which pattern fits depends less on risk appetite than on who owns the deployment manifest.

Pattern A · The single team, no platform involvement

One repo, one agent, a handful of tool servers. Ship the mediator with --contract pointing at files checked into the repo, no control plane. Contracts are renewed by a PR. This scales to roughly one team and is the right answer for the first one — it needs approval from nobody and it proves the model in a week.

Pattern B · The paved road

The platform team owns the base image and the CI template, so they own rungs 2 and 4 for everyone. Registration becomes a pipeline step nobody writes by hand; the mediator is already in the image. Application teams only ever touch rung 3 — request — and most of their requests auto-approve. This is the pattern that gets estate coverage, and it works because the two rungs with real setup cost are paid once, centrally.

Pattern C · Federated by business unit

A control plane per BU, each with its own issuer key, policy file and approver registry, federated at the trust-anchor level. Correct when BUs have genuinely different regulators or approval chains — and the honest cost is that trust-anchor rotation becomes something a named human owns.

Pattern D · Provider-led onboarding

Inverted, and underrated. The team that owns a widely-used MCP server registers it first, publishes its pinned surface, and lets consumer teams request against it. Adoption spreads along the dependency graph rather than the org chart, and the provider gets the dependent list they never had.

Pattern E · Regulated / air-gapped

Contracts minted in a connected environment, exported as signed bundles, carried in. Enforcement is full-strength; expiry management is the hard part, so TTLs get set by what the bundle refresh cycle can actually sustain rather than by what the risk appetite would prefer.

These compose. The realistic sequence is A in one team to prove it, B to get coverage, and C only when a second regulator forces it. Starting at C is the classic way to spend a year on a platform nobody has yet used.
07

The ratchet

Inside any rung that touches traffic there is a second, smaller gradient — and it only turns one way.

mode = observe

Record, deny nothing

Every check runs and every finding is written to the evidence chain. Behaviour is byte-identical to not having deployed it. This is where you discover the connections you did not know existed.

mode = flag

Surface, still permit

Findings become alerts to owners. Drift, ceiling approach and upcoming expiry reach a human. Nothing is blocked, so nothing breaks — but the org starts reacting to the signal.

mode = enforce

Deny, fail closed

Uncontracted calls are refused. An unreachable control plane is an error, not an empty contract set — because an empty set would silently drop every contract you hold.

The ratchet exists per zone, and the zone model is what stops it from being a single estate-wide switch somebody is too frightened to flip. internal.payments can be enforcing while internal.sandbox is still observing, and a zone can never declare its way below its trust level's floor — trust = "partner" always means at least a human approver, a 7-day ceiling and delegation depth 1, whatever the rest of the stanza says.

One detail in the policy file carries more weight than it looks like it should:

[standing] max_share = 0.6 # ≤60% of active contracts may be auto-issued share_min_sample = 20 # …but only once there are this many min_callee_tier = 3 # tier 1 and 2 callees always need a human allow_write = false # a write surface always needs a human max_tools = 8 # more than eight items is not "low risk" reviewed_at = 0 # UNSET — every request escalates until reviewed

Auto-approval is what makes the register adoptable and simultaneously the widest policy surface in the system. So it is bounded in the engine, every breach escalates to a human, and reviewed_at = 0 means an unreviewed standing policy escalates everything — the correct default for a control nobody has signed off on yet.

08

Three ways adoption fails

Not hypotheticals. Each of these was a real defect found while building this, and each one is the same species: a control that reads as configured and does nothing.

The inert control

A mistyped --anchor-ky was silently ignored, so an operator believed evidence was being anchored when it was not. The anchor interval counted appends per process — and a CLI invocation is one process, so the anchor file stayed permanently empty. A public* glob failed to match bare public, which silently disabled the public-egress deny rule: present, readable, and inert.

what it costs adoption The estate believes it is protected. Discovery happens during an incident, at the worst possible moment, and it destroys trust in every other control at the same time.

The ratchet that strangles

The standing-policy share cap escalated every request forever once a single contract existed — because 1 of 1 is 100%, which exceeds 60%. A policy that is individually correct at every line, and collectively guarantees that no estate can ever bootstrap.

what it costs adoption Every request goes to a human, the queue this was meant to replace comes back, and the org concludes the tool does not work. The fix was share_min_sample: a percentage of a tiny denominator is noise, not signal.

Enforcement before identity

The issuer hardcoded enforce mode. But at rung 2 every party is Unattested — nobody has provenance verification deployed yet — so nothing could ever be minted. Enforcement was demanded before the machinery that satisfies it existed.

what it costs adoption The tool fails on first use, for the correct reason, in a way that looks like a bug. Mode is now a deployment property, which is what lets rung 2 exist at all.

All three were found by running the binaries, not by the test suite. Twenty-five passing API tests asserted response shape while the endpoint returned metadata without the artifact its only consumer needed. The lesson generalises to anyone adopting this: on every rung, ask what it would look like if the control silently did nothing — and prefer the negative assertion. The upstream never executed it. Nothing was appended. The string is absent from the bytes.

effective = contract.surface ∩ token.scope ∩ policy_decision

One line holds the technical design together. A second line holds the adoption story together, and it is the harder of the two to honour:

Every rung must shrink a surface or shorten a wait.

A control plane that only shrinks surfaces is a tax, and taxes get routed around. A control plane that only shortens waits is a convenience, and conveniences get switched off when they misfire. warden-connect is built on the claim that the same artifact can do both at once — that a narrower tools/list is genuinely easier to build against, and that approving a relationship once is genuinely faster than approving every call forever.

If that claim holds, adoption does not need a mandate. It needs a first rung small enough to climb on a Tuesday afternoon.
