Registration is a decision, not a form

An agent asking to join the estate is making a claim about itself. Admission is where that claim is either proved or recorded as unproved — and it ends with the agent holding exactly zero connections.

What happens without it

A team deploys an agent. Nobody records that it exists, nobody owns it, and nothing anywhere knows what it is allowed to reach. The first time anyone asks is during an incident.

02

The flow

Each step is labelled with which layer owns it. The badge matters more than it looks: most of the confusion about this system is people expecting one layer to answer the other's question.

1
warden-connect

Identity

The workload identity is verified against the trust bundle — a JWT-SVID, audience-bound and expiring. The token must authenticate the id being registered: a valid token for a different workload is a refusal, not a pass.

2
warden-connect

Surface acquisition

The declared surface is fetched, not asked for. This is the one stage that fails closed in every mode — a record with no pin is an entity whose surface can never be shown to have changed.

3
warden-connect

Card signature

A detached JWS over the canonical card, verified against the operator's keys. Verified against a key set the party controls, it would only prove the party signed its own claim.

4
warden-connect

Provenance

DSSE → in-toto → SLSA. A pass needs all three bindings: a trusted key, a subject digest matching the artifact being admitted, and a builder in the allowlist. A valid signature over a statement about some other artifact proves nothing.

5
warden-connect

Injection screening

Eight detectors over the declared text. This is where a poisoned skill description is caught — before any model has read it.

6
warden-connect

Tier derivation

From declared data classes and capability classes. Tier 1 and 2 route to a named architect, and the reasoning is recorded: a tier nobody can explain gets argued with rather than applied.

7
warden-connect

Pin and record

The card is canonicalised and hashed. The entity lands in the registry Pending, with a posture that reflects what was actually proved.

03

Where the boundary is

Two layers, and neither can widen the other. Removing one does not silently loosen what remains.

warden-connect

Owns this entirely

Admission is a relationship-layer question — may this party exist in the estate at all, and what do we know about it? Warden core has no view of it and needs none.

connect register agent --card … --owner …
Warden core

Not involved yet

Core enforces actions. There are no actions to enforce: the agent holds no contracts, so there is nothing for it to call. Core enters the picture at UC-04.

04

The exception paths

Where the real design lives. A main flow describes the day everything works; these describe the days that decide whether anyone keeps the thing switched on.

A1Unverifiable provenance

In observe mode the agent is admitted with posture: unattested and flagged. In enforce mode it is refused. The mode is a deployment property, not a per-request one — in early adoption every party is unattested, so enforce mode would admit nobody.

A2Screening finding

Admission blocked, with the offending text quoted to AppSec. Only four of the eight detectors may block, and only once calibrated at precision ≥ 0.98 — a screener that blocks legitimate tools gets switched off, and a switched-off control has zero recall.

A3No named owner

Refused. Ownership is enforced by the type: the owner field is not an Option, so an unowned entity cannot be constructed.

A4Re-registration with a changed card

Treated as drift, not an update. A changed surface on a live party is UC-06, and letting a re-register overwrite the pin would be a rug-pull with a friendly name.
